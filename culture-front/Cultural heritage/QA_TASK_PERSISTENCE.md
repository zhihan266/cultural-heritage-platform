## 1. 原来为什么丢失与等待

原问答页仅将问题、回复、taskId 保存到组件 `messages` 数组。离开组件后数组销毁，个人中心没有入口，也没有持久化的编号索引和详情路由。服务器任务并未被删除，但前端丢失了重新查询所需的关联。

旧查询循环跟随临时消息运行，路由卸载即取消，首次查询异常会退出等待；重新进入没有 taskId 可恢复，也没有网络退避和未知状态处理。不能据此断言实际后端某次等待的唯一原因，但这些是已确认的恢复与状态同步缺陷。

本轮不再把聊天消息当数据源：创建、任务索引、详情查询、状态监视、最终结果展示分别负责。浏览器验收还发现并修正了新轮询器间接调用原生定时器导致的 Illegal invocation 问题，最终通过了实际浏览器的多轮自动状态更新。

## 2. 真实后端能力

只读检查了路由装配、HCP 请求/Task 模型、Facade、WorkerSelector、任务查询仓储、正式终局提交、工作流 metadata 和鉴权。实际导出 OpenAPI 校验，没有仅按前端假设接口。

| 能力 | 真实接口 / 业务 | 权限与结论 |
| --- | --- | --- |
| 创建 | `POST /hcp-mad/tasks`，本前端发 `{question,use_rag}`；返回 `{task}`，编号是 `task.id` | JWT 当前账号由服务端确定；后端选择两个 Worker 和一个 Judge |
| 详情、状态、正式结果 | `GET /users/tasks/{task_id}` -> `{task}` | JWT；服务端要求 `task.user_id == 当前账号`，否则 403 |
| 个人 HCP 历史列表 | 未开放 HTTP 接口 | 仓储/内部 queries 虽有用户查询函数，但没有对应 HCP 列表路由，不能直接调用内部方法 |
| 按用户、模式、来源筛选 | 没有公开 HCP 列表筛选 API | 不编造查询参数或集合接口 |
| 完成通知 | 没有 HCP SSE / WebSocket 事件接口 | 使用真实 GET 的有界轮询，不伪造推送 |
| 模式 | HCP 请求实际支持 `use_rag` | 普通 false、知识库 true；服务端保存于 `metadata.hcp_mad.use_rag` |
| 旧消息列表 | `/rag-tasks/legacy/users/{id}/messages` | 属于另一套 RAG Task 数据，不作为 HCP 历史替代 |

`tasks.status` 的真实枚举为 `waiting,answering,aggregating,completed,failed`。阶段、检索情况和结束信息在 `metadata.hcp_mad`；这不是另一套由前端推断的 Task 状态。

正式答案只读 `task.final_result`。HCP Judge/终局提交逻辑将验证后的最终答案与 completed 状态持久化；单个 Worker `answers[].content`、私有 ContextItem、工具历史和隐藏推理均不作为最终答案或默认展示内容。

Task 未提供任务创建时间。metadata 中的 started_at / completed_at 也不能冒充 created_at。本轮列表明确显示“创建时间未提供”，不取浏览器时间造一个创建时间。

## 3. 持久化策略及限制

权威数据是后端已有 Task。浏览器只在 `heritage:qa:ids:v1:{accountId}` 保存字符串 ID 数组，不保存问题、答案、执行状态、权限、私有上下文或原始 Agent 输出。没有将 Pinia 或 localStorage 变成问答数据库，没有第二套聊天缓存。

创建取得服务端 ID 后先保存索引，再进入详情。若创建返回前仅切换站内页面，不主动取消创建请求；响应仍保存到原账号的索引，但旧回调不能把新页面跳回旧问答。此行为有浏览器回归。

每次打开工作台列表、个人中心、历史页或详情，都使用真实接口重新读取问题、模式、状态与结果。两个账号索引分开；读取后还检查资源 ID、HCP 模式及服务端 user_id，防止错配响应。真正授权仍由后端 JWT 和归属校验完成。

已知记录较多时按本地编号分页读取，每页 10 项，个人中心预览每页 5 项。这不是服务端分页，也不是全部账户历史；顺序为本浏览器索引顺序，不称为服务端创建时间排序。列表读取失败与没有本机编号分别显示。

同浏览器重新登录原账号可恢复仍保留的编号；跨标签页索引更新会重新查询。清理存储、换设备、以前只存在内存而没有留下编号的任务不能自动列出。可以输入已知编号恢复，但不能猜编号或读取其他账号私有任务。

创建结果未知且没有编号时，使用按账号隔离的 sessionStorage 标志暂停重复创建，要求核实后显式解除；该标志不是任务状态。后端没有创建幂等/按请求找回编号接口，关闭整个页面进程而未收到编号时不能保证恢复。存储不可用时明确提示保留当前详情链接，不声称本机记录已保存。

## 5. 自动更新流程

1. 校验非空问题，发一次真实创建请求，等待 `{task.id}`，不将创建成功当成执行完成。
2. 保存真实编号，跳转详情，立即 GET 该任务。
3. 服务端尚未结束时按配置继续查询，收到 completed 后只展示有效 final_result。
4. failed 停止自动等待并展示安全说明；不显示执行堆栈、内部恢复记录或私有工具历史。
5. 页面切换/卸载取消本地 GET 与定时器，不调用取消后端任务接口。
6. 再次进入详情重新 GET；运行中的任务重新启动本次有界查询预算，已完成的直接展示服务器结果。

因此正常完成不需要刷新整个网页。浏览器已验证先看到执行中，再自动出现正式答案，并验证终态后不再发定时 GET。

## 6. 轮询与竞态设计

`src/utils/qaPolling.ts` 是唯一详情轮询实现：

- 间隔常量 2500 ms，自动查询预算 180000 ms；单次 GET 还受既有 Axios 10 秒超时约束，预算在每轮请求前检查。
- 使用上轮结束后安排下一轮的单次定时器，不用 setInterval；上一轮未完成时不发下一轮。
- 启动/切换先增加 generation、清定时器并 abort，旧响应不进入新任务/新账号；组件额外校验当前身份与路径。
- 断网、超时、5xx 是查询失败，不将 Task 状态改成 failed。按 2.5、5、10、15、15 秒退避，连续第 6 次失败停止，允许稍后核对。
- 401/403/404 等访问错误停止并清除可见旧详情；401 仍沿用全局会话清理和登录跳转。
- 隐藏页面暂停读，返回可见时对仍在等待/退避/预算暂停的任务重新核对。完成/失败不因普通可见性切换重新开始定时查询。
- 浏览器支持 Web Locks 时，以账号 + 编号协调详情读取，尽量避免多个可见页面同时读同一任务；不共享缓存结果。列表仍有自己的按需快照请求，不声称全站网络请求严格去重。
- 轮询资源属于页面，后端执行独立于它；没有前端自动执行/重试模型的逻辑。

| 服务端情况 | 前端监视行为 |
| --- | --- |
| waiting / answering / aggregating | 串行查询最新快照 |
| completed + 有效 final_result | 展示正式结果并停止定时器 |
| completed + 空结果 | 最多核对 3 次，仍为空则显示一致性异常；不取 Worker 答案补位 |
| failed | 显示执行失败并停止 |
| metadata 的 review_failed | 明确评审暂停，停止自动等待；手动按钮仅查询，不是模型执行重试 |
| 未识别 Task 状态 | 显示未知状态并停止，不能无限解释为正在回答 |
| 超过预算 | 暂停本次查询，说明任务仍保留，可稍后查看；不伪造失败/完成 |
| 网络问题 | 独立显示查询异常/退避，不覆盖服务器业务状态 |

监视状态不写入 task.status，也不落本地权威缓存。未知、暂停、异常、预算到期都保留手动“核对最新状态”入口。

## 9. 剩余接口缺口

- 没有 JWT 当前用户的 HCP 历史集合及模式/来源筛选，不能完整跨设备恢复或恢复已丢失编号。内部仓储方法不等于公开 API。
- 没有创建请求幂等/按请求恢复编号 API，创建响应完全丢失时无法凭客户端重建 taskId。
- 没有 HCP 创建时间字段、来源片段明细、事件推送、会话列表。本轮不假造这些字段或能力。
- 众包列表等能力在工作区有独立并行改造；不作为本轮 HCP 问答的接口缺口或修改成果，也没有由本轮编辑其后端。

可实现目标已经落地：已收到编号的真实任务可以在当前浏览器离开、重入、刷新和重新登录后重新查询；个人中心按账号隔离。不能承诺清空数据、换设备或从未保存编号后的自动恢复。
