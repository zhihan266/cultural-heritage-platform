## 1. 一句话判断

**这是一个面向文化遗产问答、具有工具调用和 RAG 增强的多模型协作后端原型，已经体现基础工程思考，但高级检索集成、可靠性和验证仍未闭环。**

它比“上传 PDF 后调用一次模型”多出了任务生命周期、多个候选答案的持久化与汇总、公共/临时知识分离、工具循环和一套检索评估代码。真正的差异在这些组件如何协作，而非技术名称的数量。

对 AI 应用 / RAG 实习，这是可以作为主项目展开的个人工程项目，前提是能解释代码，并先修好可复现的演示路径。当前直接展示仓库，会暴露接口装配错误和测试漂移。对 Python 后端实习，它能证明异步调用、事务边界、身份认证与模块拆分方面的尝试，但数据库约束、幂等、权限和部署仍是明显薄弱点。对 Java 后端岗位，它提供可迁移的工程讨论材料，不能替代 Java 生态和后端基础知识。

**阶段判断：基础工程化，正在集成更完整的检索能力。** 不宜定位为“接近生产级 RAG”“自主多 Agent 平台”或“高并发企业知识库”。本评估不据此推断面试通过率。

## 3. 真实业务主线

### 3.1 创建任务到最终答案

1. 用户登录后创建任务，填写问题、回答格式、业务 AI 列表、人工人数。后端用登录账号覆盖请求中的发布者 ID。
2. 任务先提交数据库，再交给同一 Web 进程的 BackgroundTasks。
3. 编排器读取任务，用带 `status=waiting` 条件的 UPDATE 原子领取，提交后进入 answering。
4. 只有 RAG 模式会加载上下文；一次加载后共享给业务 AI、聚合和评分。失败会记录日志并退回无 RAG 回答。
5. 各业务 AI 并发执行。每个 AI 已接入模型 → 工具调用 → 工具结果回填 → 再次模型请求的循环，最多 5 轮。
6. 成功答案分别落库；编排器重新统计已保存答案。没有可用答案则失败，存在答案则继续聚合，允许部分 AI 失败。
7. 聚合角色先生成最终答案，再通过另一次请求给候选答案评分，最后标记 completed。
8. 发布者可提交最终审核；系统用审核文本与原答案的字符序列相似度调整回答者信誉分。

关键代码：[user_router](../app/modules/task/api/user_router.py)、[orchestration](../app/modules/task/application/orchestration.py)、[repository](../app/modules/task/infrastructure/repository.py)、[ai_answers](../app/modules/task/application/ai_answers.py)、[aggregation](../app/modules/task/application/aggregation.py)、[review](../app/modules/task/application/review.py)。

**主线已连接，但完成条件不统一：** 自动 AI 流程不等待人工人数满足；纯人工任务会跳过 AI 编排，需要手动完成。人工先领取还可能把 waiting 改为 answering，使随后启动的 AI 编排跳过。不能说“系统保证收齐所有人机答案后统一聚合”。

### 3.2 Agent 到什么程度了

已超过单纯把多个文本请求放入 asyncio.gather：每个业务 AI 的实际回答入口会调用 [run_tool_calling_agent](../app/modules/agent/tool_calling.py)，通过注册表执行模型选择的工具，并按 tool_call_id 回填结果。

但协作仍由固定中央流程组织：业务 AI 独立回答，聚合模型读这些答案，没有 Agent 间通信、任务分解协商、互评辩论、共享长期记忆或自主路由。业务 AI 的角色提示也未形成明确专业分工。

准确名称是“中央编排的多个工具调用 Agent 与聚合角色”。是否值得多模型，必须和单模型、单工具 Agent 比较质量、延迟、请求次数及成本；目前没有这样的证据。

### 3.3 RAG 的实际入口

| 入口 | 实际策略 | 状态 |
| --- | --- | --- |
| /admin/rag/documents | Parser → Cleaner → Splitter → Embedding → Milvus upsert | 已有 HTTP 入库；原 README 的“仅脚本入库”过期 |
| /rag/retrieve | DenseRetriever | 路由与工厂已连接；依赖真实外部服务 |
| RAG 任务，无附件 | 公共 Dense，默认 top_k=4 | 已接入任务主线 |
| RAG 任务，有附件 | 一次 query embedding，公共 Dense 3 条 + 内存余弦 2 条 | 已接入；不是跨来源全局重排 |
| /rag/answer | 工厂意图为 Hybrid → Rerank → LLM | HTTP 依赖装配错误，当前不可宣称贯通 |

Hybrid 和 Rerank **不是只有文件名或 TODO**：Milvus 建表定义了 BM25 function、稀疏字段和索引；Hybrid 执行 Dense 与 BM25 两路搜索并用 RRF 融合；Reranker 通过 HTTP 返回候选文档索引和评分。问题在于没有统一接入实际入口，且存在结果数量错误。

[composition](../app/modules/rag/composition.py)、[task_context](../app/modules/rag/task_context.py)、[Milvus 实现](../app/modules/rag/infrastructure/vectorstore/milvus_vector_store.py) 是核对真实路径的核心。另一个本地 BM25Retriever 未被这些入口使用，不能把它与 Milvus BM25 算作两项已经接入的能力。

## 5. 最值得展开的四个技术点

### 5.1 任务并发与事务边界

这是当前最容易用代码讲清楚、最有后端价值的部分：

- 条件 UPDATE 与受影响行数决定谁领到 waiting 任务，优于先查状态再无条件改状态。
- 不跨并发分支共享 SQLAlchemy Session；部分同步数据库工作使用 to_thread。
- gather(return_exceptions=True) 隔离单个 AI 失败。
- 以已提交答案数量判断能否聚合，区分“模型调用返回”和“答案成功持久化”。
- 聚合前提交状态，不把慢模型请求包在一个长期数据库事务中。

应该掌握 SQL 层面的竞态、事务提交时机、重复执行与进程崩溃之间的区别。不能据此宣称 exactly-once：领取后进程退出仍可能留下卡住任务，手动 finish 与后台流程也没有完整互斥。

### 5.2 RAG 的边界和双来源检索

Parser、Cleaner、Splitter、EmbeddingProvider、VectorStore 的拆分有实际替换和测试价值。公共与临时知识分离是贴近用户问题的设计；同一 query embedding 复用、统一上下文供多个 AI 使用，也体现了避免重复工作的一面。

需要讲得出数据从文件到 chunk 再到检索结果的字段变化。当前页码与 offset 在预处理阶段存在，却没有完整持久化到向量库，这正是设计与实现之间的缺口。

固定公共 3 / 临时 2 能保留两种来源，但未根据相关性统一排序，也未考虑某一来源为空后的配额补足与长文本 token 预算。它是一版可解释策略，不是已经调优的最佳方案。

### 5.3 工具调用的完整消息循环

可以讲清工具定义如何变成模型 schema、如何解析 arguments、怎样通过注册表选择实现，以及为什么下一轮需要同时保留 assistant(tool_calls) 与匹配 tool_call_id 的 tool 消息。

当前遗产查询是正式名称的结构化查询；web_search / fetch_webpage 是 Tavily 适配，配置密钥才启用。工具执行异常会终止当前 Agent，而不是把错误送回模型修正。最多 5 轮只限制模型回合，不等于最多 5 次工具执行，也不是总耗时预算。

面试价值在协议和执行控制，而不是“封装了三个函数”。

### 5.4 已开始做可检验的检索评估

仓库已有真实数据文件、分类、指标实现和报告，优于只展示几条成功问答。可以讨论多相关文档标签、召回与排序的区别，以及哪些失败样本需要 BM25 或 rerank。

但当前最值得讲的是“已建立初步评估方法，并识别其局限”，不能包装成已证明的算法提升。

## 6. 最需要正视的问题

优先级含义：P0 为阻碍当前功能演示的直接缺陷；P1 为对外运行前必须处理的正确性/权限问题；P2 为影响维护、解释和实验可信度的问题。若准备公网部署，权限问题应立即提升优先级。

### 6.1 已确认的代码与集成缺陷

| P2 | 已有 Milvus 集合直接复用，未校验维度、稀疏字段或 embedding 版本 | 新 Hybrid 代码与旧集合可能不兼容；配置切换不等于数据迁移 |
| P2 | 同步 Milvus 构造、search/upsert/flush 在异步路径中调用 | async 函数并不自动让 SDK 非阻塞；并发负载下可能阻塞事件循环，尚无压测量化 |
| P2 | requirements 缺 python-multipart，部分关键依赖未固定；部分脚本导入旧模块/使用旧模型配置 | 干净环境和评估复现不可靠，需要依赖与脚本分层清理 |

还应注意：账户用户名缺数据库唯一约束；配置中部分正数/有限值约束缺失；Embedding Provider 的 timeout 参数未直接用于请求，实际超时依赖外部 HTTP Client。上述问题有工程价值，但不应让面试叙述被零散缺陷淹没。

### 6.2 可靠性、上下文与生命周期

BackgroundTasks 是进程内执行，不保证服务重启后继续任务。工具 loop 有单次模型超时和轮数限制，但没有整个任务 deadline、全局并发上限、取消或恢复。注册模型的健康状态主要靠启动和手动检查更新，不能代表持续在线。

RAG 出错时选择 fail-open 可以提高回答可用性，但也会把“基于资料”变成“模型自行回答”；这个降级目前主要出现在日志中，未作为任务结果字段呈现。若业务要求严格依据资料，应设计明确的拒答/降级策略，而非把无异常当成功。

临时向量不写公共库，仍不代表临时文件会消失：成功任务文件没有 TTL。公共文档内容变化会生成新 document_id，旧向量不会自动删除；delete_by_document 尚未实现。文件内容哈希解决的是稳定标识的一部分，不是完整文档生命周期。

Context 有来源区分，但缺少统一 token 预算、检索去重和工具结果累积控制；rerank 数量错误会加重这一问题。工具轨迹、检索来源和各阶段耗时没有完整持久化，排查失败依赖日志与 print。

### 6.3 评分应如何解释

必须区分三个字段/过程：

- Answer.score_snapshot：提交时的回答者信誉快照。
- Answer.weight：聚合模型给单条答案的评分，当前没有据此加权投票。
- Account / AiAgent.score：用户最终审核后，用 SequenceMatcher 文本相似度调整的信誉。

聚合模型没有独立真值，可能偏好自身风格或重复错误。字符相似度衡量文本接近程度，不等价于事实正确性。写入名为 training_signal 的 metadata 也没有触发训练；这里不存在强化学习或微调闭环。

## 7. 架构评价：有价值，但边界还不一致

| 维度 | 评价 |
| --- | --- |
| Package by Feature | account / agent / task / rag / tool / heritage 按业务组织，定位功能比全局 controller/service 大目录更直接 |
| 抽象与 Provider | RAG 的解析、向量化和存储契约具有真实用途；工具 registry/executor 也有协议与执行分离价值 |
| composition / DI | 集中装配方向正确；工厂签名变化未同步 HTTP 入口，说明边界缺契约约束 |
| domain 纯度 | task/domain/models 同时放 ORM/Pydantic 并依赖数据库；并非严格纯领域模型 |
| service 边界 | 部分 service 抛 FastAPI HTTPException，RAG 问答直接访问 agent repository 和模型函数，跨层耦合仍在 |
| 数据库与状态 | 有事务意识和原子领取，但唯一约束、完整迁移、人工/AI 状态规则还不足 |
| 异步与容错 | 并发调用及单 AI 失败隔离有实质内容；同步基础设施调用、缺并发预算与恢复削弱了可靠性 |
| 可测试性 | 可注入的 Session 工厂与检索接口便于测试；当前 mocks、签名和入口装配已经漂移 |
| 可维护性 | 功能边界有所改善，但 settings 单例与 get_settings 混用，调试重复处理和失效模块增加维护成本 |
| 可观测与部署 | 有日志、AI 健康字段；缺请求/任务执行轨迹、指标、依赖 readiness、CI 和可复现部署 |

不建议为了“更像 DDD”继续拆出更多空目录。可以在后续局部修复中清除未使用抽象、统一装配与配置，保留真正带来替换点的边界。大段复述代码的注释、单纯搬文件、为一次调用增加转发层，面试价值有限。

主线建议固定为：**资料与工具增强的问答任务如何可靠完成，以及如何用评估证明检索设计有效。** 信誉排行榜可以作为业务补充，不宜占据技术介绍中心。

## 9. 面试追问与应掌握的深度

| 问题 | 需要讲到的程度 | 当前诚实回答的边界 |
| --- | --- | --- |
| 为什么需要多 Agent？ | 给出候选答案多样性假设；设计单模型、单工具 Agent、多模型+聚合对照，比较质量/延迟/成本 | 尚未证明收益；同类模型可能相关性高并共同出错 |
| Agent 怎样协作？ | 画出中央编排、独立工具循环、持久化、聚合；解释 tool_call_id 和停止条件 | 没有互相讨论或自主分工 |
| 如何防止任务重复执行？ | 写出带 status 条件的 UPDATE；说明 rowcount 与独立 Session；分析领取后宕机 | 领取防重不覆盖 finish、review 和崩溃恢复 |
| 一个模型超时怎么办？ | 解释 gather 的异常收集、已保存答案判断、聚合失败分支；区分单次超时与总 deadline | 已隔离部分失败；没有系统级重试/总时间预算 |
| 人和 AI 同时回答会怎样？ | 推演 worker 先领任务和 AI 先结束两条时间线，指出状态竞争 | 当前没有一致的“全部完成”规则 |
| chunk_size 为什么是 800、overlap 为什么是 120？ | 说明这里按字符切分；边界优先、语义完整性与重复开销；提出可比较实验 | 当前默认值不是测出来的最优值 |
| EmbeddingProvider 有什么意义？ | 讲协议隔离、批处理、query/document 差异、输出校验、mock；理解换模型要重建向量 | 不能仅改 model 名就保证索引兼容；normalized 标记不执行归一化 |
| 为什么 Milvus / HNSW？ | 解释当前向量与关键词同库的便利；HNSW 的近似检索、内存/召回/延迟权衡，知道 M=16、efConstruction=200、search ef=64 的含义 | 未基于现有小语料证明它优于更简单存储，也未做参数压测 |
| 为什么 Hybrid 和 RRF？ | Dense 补语义、BM25 补专名/关键词；解释按排名融合而非直接相加异尺度分数，当前 RRF 参数为 60 | 已实现策略，但任务入口未接入、效果未对比 |
| 为什么 rerank？ | 区分候选召回与精排成本；说明原始候选 index 映射、最终 top_k、评分语义 | 当前数量契约错误；返回 hit.score 仍是原召回分数，不能称 rerank 置信度 |
| 怎么保证答案有依据？ | 追踪来源字段、解释空召回处理、设计引用支持度/正确性检查与拒答集 | 拼接资料和返回 sources 都不等于逐句 grounding |
| Aggregator 是否只是再调一次模型？ | 承认最终答案生成是一次模型请求，随后评分另一次；讨论冲突、偏差、可验证证据 | 没有投票算法或独立裁判真值，当前 weight 未做融合 |
| Redis 用来干什么？ | 说明 JWT 签名、Redis 当前 token、黑名单与 TTL 各自作用；解释为何有状态会话 | 不是 RAG 缓存或队列；开发内存降级不跨进程、不持久 |
| 怎么评估、怎么复现？ | 手算 Recall 和 RR，解释 chunk/doc 粒度、固定语料/模型版本、难例、成本和随机性 | 当前报告是小样本历史 Dense 结果，不能宣传综合准确率 |
| 为什么用 vLLM / Ollama？ | 解释应用依赖的是服务协议；区分 Chat / Embedding / Rerank 的契约与模型支持 | 仓库是调用方，没有推理引擎优化实现；不能声称服务兼容所有版本 |
| 如何部署并排查故障？ | 从配置、schema、启动、readiness、依赖超时、日志追踪到失败任务恢复逐层说明 | 目前没有完整部署验收、CI 或执行轨迹，只有基本启动和健康检查 |

准备时应能脱离框架名手写关键伪代码和 SQL，并用一个具体失败场景解释设计。不要把“接口使用异步”解释为所有操作都不阻塞。

## 10. 下一步只做三件高收益的事

### 第一优先：把一条主链修到可重复演示

修复 HTTP 工厂类型、rerank 最终数量、断裂导入、缺失依赖和过期测试。让普通任务、公共 RAG、附件 RAG 的策略选择清楚可见，先明确一个稳定默认策略，再保留实验策略。

验收标准：同一套准备步骤可重复完成上传 → 检索 → 创建任务 → 工具调用/候选答案 → 聚合 → 查询结果；自动测试覆盖真实依赖装配、结果数量和模式分支。服务不可用时应给出可解释的失败或降级状态。不要通过把实际依赖全 mock 掉来掩盖入口错误。

### 第二优先：用对照实验决定检索复杂度

固定语料、模型、chunk 规则和 query instruction，统一对比 Dense、Hybrid、Hybrid+Rerank。补充困难样本和无答案样本；分开记录候选召回、精排、生成，观察 Recall、排序质量、引用支持度、延迟与请求成本。

验收标准：一份能复跑、有配置和数据版本、包含失败样本解释的报告。没有收益也可以是可信结果：可以据此选择较简单默认策略。多 Agent 对照随后沿相同方法做，不急着增加 Agent 数量。

### 第三优先：补齐可靠性与权限的最小闭环

明确人工与 AI 的完成规则，为 finish/review 建立幂等边界，保护模型配置和公共索引接口；记录 task_id 对应的阶段、检索来源、工具调用、耗时、错误及降级情况。补充必要 schema 迁移、附件清理策略和部署说明。

验收标准：重复完成/审核不会重复副作用；未授权请求不能修改配置或公共库；能通过一条任务轨迹解释失败。再按实际恢复需求选择持久队列，不必同时引入多种中间件。若准备公网开放，应先做这一项中的权限与地址限制。

暂时不值得投入：

- Agent 通信协议、复杂辩论图和长期记忆：还没有证明当前协作的收益。
- 微调、强化学习、奖励模型：现有评分不是合格训练数据或可靠奖励。
- GraphRAG、分布式索引和多套向量数据库：目前没有数据规模或召回失败证据支持。
- 为展示框架名而迁移 LangChain / LangGraph，或继续拆空领域层：优先修复现有边界。
- 新前端与大规模 UI：本轮目标是后端技术表达，Swagger 和可重复脚本足以支持第一轮演示。

## 12. 三分钟介绍示例

我做的是一个面向文化遗产问答的后端。用户可以提出问题、选择多个业务 AI，也可以提供临时资料。系统保存各 AI 的候选答案，再由聚合模型生成最终结果；人工回答也有独立入口。

我主要围绕两条链做设计。第一条是任务执行：任务先落库，用带状态条件的数据库更新领取，然后并发执行 AI。每个分支独立保存答案，一个模型失败不会直接让其他结果丢失，最后根据数据库中真正保存的答案决定是否聚合。这里我重点考虑了并发和事务边界，但目前还是进程内后台任务，尚未完成重启恢复和全流程幂等。

第二条是资料进入回答的过程。公共文档经过解析、清洗、切分和批量向量化后进入 Milvus；用户附件只在任务处理中建立内存向量。两类检索共用问题向量，按来源构造上下文，并共享给回答、聚合和评分。模型调用还接入了工具循环，可以查询文化遗产数据，配置后也能搜索和提取网页。

我把模型、存储和业务编排分开，主要是为了替换和测试，而不是为了多加层。最近也实现了 BM25 混合检索和重排序，不过目前任务入口仍主要用 Dense，直接问答接口还有装配问题，不能把高级检索说成全部完成。

评估方面已有 40 条标注问题和 Dense 历史报告，但它只测小样本检索，不代表回答正确率，也没有证明多 Agent 的收益。下一步我会先修通主链，再做同条件检索对照，并补任务权限、幂等和执行轨迹。这个项目最想展示的是，我能把模型调用组织成可解释、可验证的业务流程，也能识别它目前不可靠的地方。

## 13. 深挖时沿哪条主线展开

优先顺序：

1. **一个任务如何可靠完成：** HTTP 创建 → 提交事务 → 条件领取 → 并发分支 → 答案落库 → 聚合/评分。用重复执行、部分失败、人工竞争、进程退出四种情况解释边界。
2. **一份资料如何支持答案：** raw file hash → parser/cleaner/splitter → embedding 校验 → Milvus 或内存 → query embedding → retrieval → context。指出 metadata 丢失、固定配额和 token 预算缺口。
3. **如何证明设计有用：** 用难例解释 BM25/rerank 的动机，明确历史评估口径，设计同条件对照；用质量/成本比较决定是否需要多 Agent。
4. **工具循环如何受控：** schema、注册白名单、参数解析、tool_call_id、错误传播、最大轮数，以及为什么还需要总预算与轨迹。

这样能把模块数量转化为几条可验证的工程论证。真正有区分度的表达是：知道代码解决了什么、没有解决什么，以及下一次实验或修复将验证哪个假设。
